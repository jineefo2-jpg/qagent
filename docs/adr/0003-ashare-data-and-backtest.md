# ADR-0003 · A 股数据底座与回测引擎 —— 存储、引擎、LLM 定位三项决策

- **Status**: Proposed · 2026-08-18
- **Phase**: P1 + P2（A 股量化平台首期），与券商 Phase X 系列并行、互不耦合
- **Scope**: 本 ADR 只裁决三个关键选型。数据模型、因子清单、铁律条文见
  [设计规格](../specs/2026-08-18-ashare-quant-platform-design.md)；工程契约见
  [架构方案](../architecture/ashare-platform-architecture.md)。
- **Does not amend**: ADR-0001 / ADR-0002。本期不接触 `brokers/`、`risk_gate.py`、
  `intent_store.py`（规格 N2 / N6），交易安全模型完全不变。

---

## 1. Context

现有 QuantAgent 是「LLM 驱动的工具调用 + 半自动下单」系统：数据取自 yfinance / akshare
实时接口，工具返回即时结果，没有历史数据底座，也没有可复现的回测能力。

新需求是在同一个进程里长出一套**A 股周频量化策略平台**：全市场 15 年 PIT 数据、
横截面因子库、可复现回测、周频调仓清单。约束：

1. **单机、单用户**。一台开发机或一台 VPS，没有运维团队，没有云预算。
2. **数据规模确定且有上界**：全 A 含退市 ≈ 5,700 只 × 4,030 交易日 ≈ 1,250 万行日线，
   加派生因子表 ≈ 3,900 万行。**周频调仓，不需要分钟/逐笔数据**（规格 N4）。
3. **访问模式是「批量列扫描 + 横截面聚合」**，不是「高并发点查 + 事务写入」。
   典型查询：「取 2015-06-12 全市场 3,000 只股票过去 250 个交易日的收盘价」。
4. **写入是每天一次批量追加**，不存在并发写、不存在行级更新竞争。
5. **正确性优先于一切**：整套设计的核心价值是「不骗自己」，八条铁律（D1–D8）都是
   为防止前视/幸存者/过拟合而设。任何为了省事而削弱可复现性的选择都不接受。
6. **不能污染现有系统**：`server.py` / `quant_agent.py` / `brokers/` 的既有安全模型不变，
   A 股功能必须是可选依赖（`try: import ... except ImportError`，本仓库既有惯例）。

## 2. Decision Drivers

| 优先级 | 驱动因素 |
|---|---|
| 1 | **可复现性**：同参数 + 同数据快照 → 同结果。这是 D7 的前提，也是整个项目的意义 |
| 2 | **零运维**：没有 DBA，没有值班。任何需要「起一个服务并保证它活着」的组件都是负债 |
| 3 | **横截面分析效率**：全市场 15 年周频回测单次 < 60 s（规格 §11 硬指标） |
| 4 | **与现有单机部署共存**：同一台机器上已经跑着 FastAPI + chromadb + sentence-transformers，内存不是无限的 |
| 5 | **可退出**：任何一个选择都要能在 1~2 周内换掉，且有明确的退出触发条件 |

## 3. 决策一 · 存储选 DuckDB，不选 Postgres / TimescaleDB

### 3.1 Decision

**原始数据与派生数据分别存两个 DuckDB 单文件**（`market.duckdb` / `derived.duckdb`），
Parquet 按年分区导出**仅作冷备与灾备重建**，不参与任何在线查询路径。

### 3.2 候选对比

| 维度 | **DuckDB（选中）** | Postgres 16 | TimescaleDB |
|---|---|---|---|
| 部署形态 | 进程内库，一个文件 | 独立服务 + 用户/权限/连接池 | Postgres 插件，同左 |
| 运维成本 | 0 | 安装、备份、升级、监控、磁盘告警 | 同左 + 插件版本兼容 |
| 横截面列扫描 1,250 万行 | 列存 + 向量化，亚秒级 | 行存，需覆盖索引，秒级 | 压缩后接近列存 |
| 「取 3,000 只 × 250 日收盘价」 | 一次扫描 + zone map 剪枝 | 索引扫描 + 大量随机 IO | 分块剪枝，较好 |
| 与 pandas/numpy 互操作 | `.df()` 零拷贝（Arrow） | 走 libpq 序列化，明显开销 | 同左 |
| 并发写 | ✕ 单写者，跨进程互斥 | ✓ MVCC | ✓ MVCC |
| 事务/行级更新 | 弱（够用：批量 DELETE+INSERT） | 强 | 强 |
| 备份/回滚 | 复制一个文件 | pg_dump / PITR / 归档 | 同左 |
| 数据大小上限（实践） | 单机磁盘，百 GB 量级舒适 | 同左 | 更适合 TB 级 |

### 3.3 Rationale

- **访问模式完全匹配列存**。本系统 95% 的查询是「按日期范围取多列、跨数千标的做横截面」，
  这正是 DuckDB 的主场。Postgres 要达到同等性能得堆覆盖索引，索引体积会接近数据本身。
- **零运维不是「省事」，是「可靠性」**。单人项目里，一个需要独立维护的数据库服务
  最可能的故障模式不是性能不够，是**某天忘了它在跑、磁盘满了、或者升级后起不来**。
- **可复现性直接受益于单文件**。「这次回测跑在哪份数据上」在 DuckDB 里就是一个
  文件的 inode + 快照指纹；在 Postgres 里要靠额外的快照机制才能回答同样的问题。
- **本项目没有 Postgres 唯一擅长的场景**：无并发写、无行级更新、无多客户端事务、无权限模型需求。
- **两个文件而不是一个**：`factor_value` 是全库最大的表（≈ 3,900 万行）且是**可重算的派生数据**。
  分开的唯一理由是**回滚粒度** —— 因子算错要回滚因子，不该连行情一起回滚；
  行情补数要回滚行情，不该丢掉几十分钟算出来的因子。合并成一个文件也能跑，只是回滚会连坐。

### 3.4 Costs（这个选择的真实代价，不粉饰）

| 代价 | 说明 | 缓解 |
|---|---|---|
| **跨进程无法一写一读** | DuckDB 以读写模式打开会取文件独占锁；常驻的 `server.py` 只读连接存在时，`ingest.py` 根本拿不到写锁。**这是选型当天就必须解决的问题，不是「以后再说」** | 影子文件 + 原子替换（架构方案 §10.2）：写发生在另一个文件上 → `validate` → `os.link` 存版本 → `os.replace`。顺带白送了备份与秒级回滚 |
| 读者看到的是快照而非实时 | promote 后读者仍持旧 fd，直到下次 `open_db()` 检测 inode 变化才重连（≤ 10 s 延迟） | 对每天更新一次的数据，这不是问题；反而保证了单次回测全程数据一致 |
| 每次 promote 要复制一次库文件 | 0.9 GB，NVMe 上 1~2 s | 可接受；且复制的是 staging 的准备阶段，不占用服务时间 |
| WAL 陷阱 | 带 `.wal` 的库文件被单独 `os.replace` 换走 = 损坏 | promote 前强制 `CHECKPOINT` + 关闭连接，写进 runbook |
| 文件格式跨版本兼容性 | DuckDB 大版本升级可能改存储格式 | `requirements.txt` 锁大版本（同 `tigeropen` 的处理方式）；Parquet 冷备是跨版本逃生通道 |
| 没有权限模型 | 无法用 GRANT 实现 D1 | 用 `read_only=True` 连接 + 静态检查替代（架构方案 §7），效果等价且更容易验证 |

### 3.5 退出条件与成本

| 触发条件 | 动作 | 成本 |
|---|---|---|
| 出现真正的并发写需求（盘中实时更新 + 同时查询） | 迁 Postgres/Timescale | 1~2 周：schema 基本可平移（都是标准 SQL），`query.py` 是唯一数据出口 → **只需改这一个文件的连接层与方言**。这正是 D2「唯一出口」设计的附带收益 |
| 数据量 > 100 GB（引入分钟线/逐笔） | 先做分区表 + 按年分块，仍留在 DuckDB | 2~3 天 |
| 多用户并发查询 > 10 QPS 持续 | 迁 Postgres | 同上 |

**退出成本被 D2 显著降低**：因为全系统只有 `ashare/data/query.py` 一个文件接触数据库，
换存储引擎不需要改因子、回测、策略、工具层的任何一行。这是「唯一出口」这条铁律
除防前视之外的第二个收益，值得单独记一笔。

## 4. 决策二 · 自研周频横截面回测引擎，不用 qlib / backtrader / vectorbt

### 4.1 Decision

自研 `ashare/backtest/`，`engine.py` ≤ 400 行只做编排，实体逻辑分到
`portfolio.py` / `execution.py` / `cost.py` / `metrics.py` / `guards.py`。

### 4.2 候选对比

| 维度 | **自研（选中）** | qlib（微软） | backtrader / vectorbt |
|---|---|---|---|
| 范式 | 周频横截面（截面排序 + 权重分配） | 横截面 + ML pipeline，范式最接近 | backtrader 事件驱动逐标的；vectorbt 向量化但偏单标的信号 |
| PIT 财报（D3：键是 `ann_date`） | 自己控制，语义明确 | 有 PIT 支持，但依赖其数据格式与 `.bin` 存储 | ✕ 基本不涉及 |
| 一字涨跌停 / 停牌不可交易（D6） | 显式 `get_tradable_mask` | 需自己写 `Exchange` 子类 | 需自己写 |
| A 股成本模型（印花税单边、过户费） | 30 行 | 可配置 | 可配置 |
| T+1 开盘成交语义 | 显式 | 可配 | backtrader 可；vectorbt 需绕 |
| 学习/适配成本 | 0（但要写 1,200~1,500 行） | 高：要接受其数据层（`.bin` + `qlib.init`）、表达式引擎、Recorder 体系 | 中 |
| 依赖体积 | 只用 pandas/numpy（已装） | 拉入一整套框架与固定目录约定 | 中等 |
| 与 DuckDB 数据层的耦合 | 天然 | 需要写 adapter 把 DuckDB → qlib 格式，或直接改用 qlib 的数据层（那 DuckDB 就白选了） | 需要 adapter |
| 调试与「看懂每一行为什么这么算」 | 完全透明 | 需要读框架源码 | 中 |

### 4.3 Rationale

- **需求面很窄**：周频、纯多头、横截面排序、三条约束、四项费用。这是回测引擎能力
  空间里非常小的一块。为这一小块引入一整套框架，然后花时间学它、绕它的假设、
  给它写数据 adapter —— 净成本高于自己写。
- **框架的假设会反噬铁律**。D6（T+1 开盘成交、一字板不可交易、停牌保留原仓位）、
  D8（只用后复权）、D3（`ann_date` PIT）这三条都是**成交与取数语义**层面的约束。
  用框架就得把这些约束翻译成框架的扩展点；翻译过程中的每一个「差不多」都是一个
  静默的前视偏差。**这套系统的全部价值就是不骗自己**，把成交语义交给别人的默认值，
  等于把最核心的东西外包出去。
- **qlib 会架空存储选型**。qlib 有自己的 `.bin` 数据层；要用它就得把数据灌进去，
  DuckDB 变成一个中转站。两套真值 = 两套 bug。
- **规模可控**：真实实现量 1,200~1,500 行（`engine.py` 只占 400），
  这个量级一个人能完整持有，且能被单元测试完全覆盖（D6 三个语义各一个单测）。
- **有客观的正确性验收**：规格 §5.6 用已知异象反测引擎 ——
  `reversal_20` / `turnover_20` 的 10 分层若跑不出显著单调性，判定为引擎或数据有 bug。
  自研引擎能对这条断言负责；用框架时，跑不出来你不知道该怀疑谁。

### 4.4 Costs

| 代价 | 说明 | 缓解 |
|---|---|---|
| 1,200~1,500 行要自己写、自己测 | 约 8~11 人日 | 分模块 + D6 三个语义单测 + §5.6 异象反测 |
| 没有社区检验过的边界处理 | 除权、退市、停牌、涨跌停的边角情况容易漏 | 五闸（尤其闸 3 shuffle 对照）能捕捉大部分「结果好得不真实」的 bug |
| 指标实现可能与业界口径有细微差异 | Sharpe 年化系数、最大回撤区间定义等 | `metrics.py` 每个指标写明公式与年化假设；与公开指数数据对拍一次 |
| 未来要做日内/多空/期货会推倒重来 | 引擎假设了周频纯多头 | 规格 N4 已明确不做日内。真要做时再评估框架，那时需求也清楚了 |

### 4.5 退出条件

| 触发条件 | 动作 |
|---|---|
| 需求扩展到日内 / 多空 / 多资产类别 | 重新评估 qlib 或 vectorbt，届时需求明确、迁移目标清晰 |
| 引擎维护成本超过 20% 的开发时间 | 说明范式选错了，重新评估 |
| 五闸反复暴露引擎 bug 且难以定位 | 用 vectorbt 做一次独立对拍，而不是直接替换 |

## 5. 决策三 · LLM 不参与决策，只做只读解释

### 5.1 Decision

LLM 层（P5）对信号表、因子表、策略参数**只有读权限**。不存在任何代码路径能让 LLM
输出写回 `factor_value` / `signal` / 策略参数。即规格铁律 D1。

本 ADR 的贡献是把 D1 从**约定**变成**机制**（详见架构方案 §7），四层：

| 层 | 机制 | 性质 |
|---|---|---|
| 1 | `query.py` 用 `duckdb.connect(read_only=True)`；写句柄只存在于三个离线 CLI 进程 | 运行时硬闸，不依赖人 |
| 2 | `scripts/check_ashare_layering.py` AST 检查导入方向 / 首参名 / 因子签名 / 写操作黑名单，由 pytest 调用 | 提交前可发现 |
| 3 | 目录级职责表：`agent_tools.py` / `report/` 禁止 import 任何 `*.store` 写函数、`brokers.*` | 评审依据 |
| 4 | 派生表带 `writer` 列，取值域不含 `'llm'`；出现即事故，等同 ADR-0001 §8 的 LLM 越权告警 | 事后取证 |

补充：新增的 A 股只读工具**不加入 `TRADING_TOOLS`**。这里要澄清一个容易搞错的语义 ——

> `TRADING_TOOLS` 不是「危险工具」标签，而是「**需要登录用户身份**」的闸。
> 现状里 `get_user_profile` / `record_memory` 也在其中（`quant_agent.py:3595`），
> 它们并不危险，只是必须知道是谁。A 股只读工具查的是全市场公开数据，没有用户维度，
> 因此不进。判据是「是否需要用户身份」，不是「是否重要」。
> 由 `tests/ashare/test_tool_registration.py` 的 `isdisjoint` 断言固化。

### 5.2 Rationale

- **LLM 输出不可回测**。同一个 prompt 两次调用结果不同（温度、模型版本、上下文顺序）。
  一个不能复现的决策环节，会让 D7（样本外只跑一次）失去意义 —— 你无法判断样本外
  结果的差异来自策略还是来自模型抖动。
- **LLM 输出不可归因**。数学模型的每一笔买入都能分解到因子贡献（`factor_contrib`），
  这是 P5「信号解释」能力的数据来源。反过来让 LLM 决策，就只剩「它说得挺有道理」。
- **提示注入是真实攻击面**。规格 §7 的知识库语料包含研报、公告 —— 都是**外部不可信文本**
  （CLAUDE.md 已有此规则）。若 LLM 参与决策，一份被构造过的公告就能影响持仓。
  只读设计从根上消除了这条链路。
- **与现有系统的安全哲学一致**。`brokers/` 子系统的核心不变量就是「LLM 输出即不可信，
  所有副作用走鉴权 + 意图 + 风控 + 审计」。A 股这边没有下单动作，但同样的原则
  平移过来就是「LLM 不产生任何持久化副作用」。

### 5.3 Costs

| 代价 | 说明 | 是否接受 |
|---|---|---|
| 放弃了 LLM 可能带来的信息增量 | 舆情、突发事件、非结构化信号无法直接进入决策 | **接受**。想用这类信息，正确做法是把它量化成因子（可回测、可归因），而不是让 LLM 拍板 |
| P5 报告质量上限受因子体系限制 | LLM 只能解释模型给出的理由，不能提出模型之外的观点 | **接受**。这正是想要的行为 —— 解释文本由 `factor_contrib` 数值驱动，不允许编造买入理由（规格 §8） |
| 多一套静态检查要维护 | `check_ashare_layering.py` 约 200 行，接口变更时要同步白名单 | **接受**。相比「某天发现 LLM 写了策略参数表」的代价，这是便宜的 |
| 用户可能觉得「AI 没在做主要的事」 | 产品叙事上要说清楚 | **接受**，且这是诚实的叙事：数学模型出信号，LLM 做解释与深度研究 |

## 6. Alternatives Considered（三项决策共同的备选）

| 备选 | 为什么否掉 |
|---|---|
| SQLite（复用现有 `data/brokers.db` 的技术栈） | 行存，1,250 万行的横截面列扫描比 DuckDB 慢一个量级；无向量化执行；「取 3,000 只 × 250 日」这类查询会成为瓶颈。技术栈统一的收益抵不过性能损失 |
| Parquet + pandas（不用数据库） | 没有主键约束、没有事务、每次都要自己写文件路由与谓词下推。等于手写一个更差的 DuckDB |
| 全内存 pandas（15 年数据一次性加载） | 峰值内存不可控（10 列 float64 ≈ 1.8 GB，加中间态易破 4 GB），且每次进程重启要重新加载。作为 `preload` 优化保留，不作为存储层 |
| ClickHouse | 列存性能确实强，但要起服务、要调配置、单机部署对这个数据量是杀鸡用牛刀。运维成本违反驱动因素 2 |
| 用 LLM 生成因子表达式再回测（Alpha-GPT 类做法） | 表面上没违反 D1（LLM 生成的是可回测的表达式），但会制造大规模多重假设检验，样本外必然崩。且规格 N5 已明确宏观层禁 ML。真要做，必须先有严格的多重检验校正框架，另开 ADR |
| 直接用 akshare（现有依赖，免费无 token） | akshare 不提供带 `ann_date` 的 PIT 财报、退市股历史、复权因子的可靠序列，D3/D5/D8 全都无法满足。保留为**补充源**（公告文本、另类数据） |

## 7. Consequences

### 7.1 正面

- 新增依赖只有 `duckdb` 与 `tushare` 两个包（BaoStock 可选），且都是可选依赖，
  未安装时 A 股功能整体降级、其余系统不受影响。
- `ashare/` 与现有 `brokers/` / `auth/` / `rag/` 完全解耦，唯一集成点是
  `quant_agent.py` 里的三行 `TOOL_REGISTRY.update(...)` 与 `server.py` 的 `/api/ashare/*` 路由。
- 存储层可替换性强（D2 唯一出口的附带收益）。
- 影子文件机制一次性解决了并发、备份、回滚三件事。

### 7.2 负面 / 需要长期承受的

- 每天 18:00 的 ingest 是**单点批任务**。它失败一次，当晚就没有新数据（但主库仍是
  上一个良好版本，服务不中断）。靠 `ingest_log` + 邮件告警 + 幂等重跑兜住。
- 回测引擎的正确性最终依赖 §5.6 的异象反测和五闸。**这两件事必须真的执行**，
  否则自研引擎的风险敞口是开放的。
- Tushare 是单一主数据源。接口变更或积分政策调整会直接影响数据可得性。
  adapter 可插拔 + BaoStock 交叉校验 + Parquet 冷备是三层缓解，但换源仍是几天的工作。
- 宏观 `publish_date` 的历史值只能靠**官方发布日历规则回填**（Tushare 不返回公布日）。
  这是 D4 在历史区间上的**已知精度损失**，必须在 `macro_indicator.publish_date_source`
  列上标记 `'rule'`，并在 `docs/oos-runs.md` 中承认。不做这个标记就是自欺。

## 8. Migration / 交付顺序

与架构方案 §12.4 一致，按可独立验收的步骤推进，每步单独 commit，
现有 canary（`python3 -m pytest tests/ -q`）保持全绿：

| 步骤 | 内容 | 验收 |
|---|---|---|
| A1 | `schema.sql`（含 `ingest_log`）+ sources adapter + 限速令牌桶 | 拉 1 天数据入 staging 库成功 |
| A2 | `ingest` 状态机 + `promote`（影子替换/版本/回滚）+ `limits.py` | 断点续传、回滚各一个单测 |
| A3 | `query.py` 全部签名 + PIT 语义 | 规格 §11 的 P1 断言全过 |
| A4 | `validate.py` 六项 + 双源交叉 + **首次全量回补** | 行数误差 < 0.1%，`ann_date` / `publish_date` 缺失率 = 0 |
| B1 | 因子框架 + pipeline + `factor_value` 落库 | 静态检查：所有因子首两参 `(as_of_date, universe)` |
| B2 | 16 个因子实现 | 覆盖率报告；`available_from` 正确 |
| B3 | 回测引擎 + 成本 + 指标 | D6 三个单测；全量回测 < 60 s |
| B4 | 五闸 + §5.6 异象反测 | `reversal_20` / `turnover_20` 分层单调性显著 |
| C1 | `agent_tools.py`（2 个工具）+ `/api/ashare/*` + 隔离测试 | `isdisjoint(TRADING_TOOLS)` 断言；layering 检查退出码 0 |

**回滚点**：A1–A4 的产物是数据文件，删掉 `data/ashare/` 即可完全回退。
B/C 步骤是纯新增代码，`git revert` 即可，不影响现有系统。
